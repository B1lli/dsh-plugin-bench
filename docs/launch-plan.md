# DSH Plugin Bench 发布与曝光计划

> 状态：GitHub 源码与 Release 已获授权；npm 因发布机器未登录而待办。目录提交、社区发帖和定向外联均未获本轮授权、也未执行。

## 问题定义

- **产品/Offer**：免费的开源 CLI 与可审计评分规范；为一个确定的 DSH artifact/commit 生成质量区间、证据缺口、Markdown 评分卡和 SVG 徽章。
- **核心用户**：第一优先是 DSH 插件维护者；第二优先是插件目录/市场维护者与准备安装第三方插件的高级用户。
- **地域/平台**：GitHub、npm 与 DSH 社区；默认中英双语，覆盖中国开发者和全球开源维护者。
- **阶段**：已完成 11 样本 pilot、独立实现审核和 GitHub 源码发布，属于 post-MVP / pre-scale。
- **预算**：假设 60 天不超过 8,000 RMB，以维护者本人 + 1 名兼职运营的正常渠道为主；不做付费刷量。
- **时间范围**：2026-08-22 至 2026-10-21，共 60 天。

| 假设字段 | 假设值 | 敏感性 | 什么会改变计划 |
|---|---|---|---|
| 团队 | 维护者 + 1 名兼职运营 | 高 | 只有维护者时，把外联和内容数量减半 |
| 发布权限 | GitHub 源码发布已授权；npm 与外联分开受控 | 最高 | npm 登录并再次执行发布门后才发布包；外联需单独授权 |
| npm 定价 | 免费开源 | 中 | 若以后提供托管审计，再单独验证付费意愿 |
| 生态规模 | 500–3,500 个候选仓库 | 中 | 目录去重后若真实可加载插件少于 300，改做深度审核而非规模榜单 |

## 上层意图

- **上层意图**：获得发布验证与可持续自然曝光，而不是单次噪声。

## 终点门

- **终点门**：G3“想用并完成激活”。看到和理解只是前置条件；终点是维护者真的生成并公开一张 commit-bound 评分卡。
- **北极星指标**：截至 2026-10-21，至少 30 个不同插件仓库公开链接或嵌入 DSH Plugin Bench 评分卡。
- **护栏指标 1**：正式争议率低于 10%（被维护者证明 commit/artifact/事实错误的公开评分卡 ÷ 公开评分卡）。
- **护栏指标 2**：至少 50% 的公开评分卡包含一条 E2+ runtime evidence，避免曝光增长把产品退化成静态打分器。
- **为什么不选 G1**：生态已经有大目录；再做一个只产生曝光的榜单没有差异。
- **为什么不选 G4**：当前没有托管服务、预算方或付费 Offer，直接优化收入会跳过理解与激活。

## 漏斗数学

`20,000 次目标曝光 → 1,000 次仓库/文档访问 5% → 200 次 CLI 启动 20% → 60 张完成评分卡 30% → 30 张公开评分卡 50%`

| 漏斗步骤 | 当前基线 | 60 天目标 | 通过阈值 | 失败阈值 |
|---|---:|---:|---:|---:|
| 目标人群曝光 | 0 | 20,000 | ≥15,000 | <8,000 |
| 仓库/文档访问 | 0 | 1,000 | 曝光→访问 ≥4% | <2% |
| CLI 启动 | 0 | 200 | 访问→启动 ≥15% | <8% |
| 生成评分卡 | 0 | 60 | 启动→完成 ≥25% | <15% |
| 公开评分卡 | 0 | 30 | 完成→公开 ≥40% | <20% |

## 受众经济

- **受众规模**：当前 [DSH Plugin Leaderboard](https://www.dshpluginleaderboard.com/) 展示约 3,498 个公开候选仓库；[dsh.pub Registry](https://dsh.pub/en/plugins/?scope=ecosystem&sort=stars) 将结构化记录与约 504 个公开 ecosystem entries 分开。按约 3,500 家候选仓库估算上界，可服务市场按 500–3,500 个候选估计，不把目录收录当作真实插件数量。
- **痛点成本**：假设维护者手工核对安装、版本、测试、权限和用户路径需 1–3 小时/版本；目录维护者批量复核成本更高。首月访谈 10 位维护者验证该假设。
- **预算拥有者**：开源项目通常没有现金预算，真正预算是维护者时间、声誉和 issue 处理成本。
- **付费意愿**：当前产品免费；预期最强意愿是贡献证据、嵌入徽章或请求审核，而非付款。
- **CAC 上限**：每个完成评分卡的现金获客成本不超过 100 RMB，或维护者人工不超过 45 分钟；超过即停付费渠道。
- **成功窗口**：首次运行 10 分钟内得到静态卡；补一条 E2 evidence 在 30 分钟内完成；30 天内验证重复使用。

## 对标案例

### 案例 1：OpenSSF Scorecard Action

- **日期/渠道**：2026-08-22 快照；GitHub Action、badge、API。
- **可核结果**：[仓库](https://github.com/ossf/scorecard-action) API 快照约 410 Stars、87 forks；官方 README 把 Action、badge、Code Scanning 和 API 串成闭环。
- **可复制动作**：“自动检查 → 可见徽章 → 点击看完整证据”的传播循环。
- **不能照搬**：它有基金会、GitHub 安全入口和托管 API，本项目当前没有。

### 案例 2：Lighthouse CI

- **日期/渠道**：2026-08-22 快照；CLI + CI + 报告。
- **可核结果**：[仓库](https://github.com/GoogleChrome/lighthouse-ci) API 快照约 7,052 Stars、713 forks；官方定位是每个 commit 自动运行、查看变化并阻止回退。
- **可复制动作**：CLI 与 CI 共用同一报告契约，结果可持续更新。
- **不能照搬**：Lighthouse 有成熟 Web 性能类别和浏览器指标，本项目仍需校准 rubric。

### 案例 3：DSH Plugin Leaderboard

- **日期/渠道**：2026-08-22；目录、搜索、提交表单。
- **可核结果**：[页面](https://www.dshpluginleaderboard.com/) 显示约 3,498 个仓库、安装状态和 Stars 排名。
- **可复制动作**：接入现有目录的提交入口，不再从零教育“插件发现”。
- **不能照搬**：它明确不是安全审计，Stars 排名不能复制为质量分。

### 案例 4：dsh.pub Registry

- **日期/渠道**：2026-08-22；结构化 Registry + ecosystem index。
- **可核结果**：[页面](https://dsh.pub/en/plugins/?scope=ecosystem&sort=stars) 显示 737 条结构化记录和 504 条公开候选。
- **可复制动作**：输出机器可读 JSON，让目录可把质量证据作为独立字段摄入。
- **不能照搬**：官方/结构化记录的来源体系不能由本项目自行冒领。

### 案例 5：dsh-score 失败对照

- **日期/渠道**：2026-08-20 本地固定 commit 复放。
- **可核结果**：[仓库](https://github.com/PerryLink/dsh-score) 0 Stars；其自评曾给 98/A，但安装显示 no-evidence。
- **可复制动作**：保留“一条命令出结果”的低摩擦。
- **不能照搬**：不复制未知维度重归一化和缺证据仍给确定高分。

## 战略选项

评分 1–5，越高越好；“风险控制”高分表示更可控。

| 选项 | 意图匹配 | 成本 | 速度 | 可执行性 | 风险控制 | 总分 |
|---|---:|---:|---:|---:|---:|---:|
| A. CLI + Markdown/SVG 卡片 + 贡献模板 | 5 | 5 | 5 | 5 | 5 | 25 |
| B. 先做独立托管排行榜网站 | 4 | 2 | 2 | 2 | 3 | 13 |
| C. 只做维护者人工深度审核服务 | 4 | 3 | 3 | 3 | 4 | 17 |

选择 **A**。它让每个插件 README 都可能成为新的曝光入口，同时传播的不是一个脱离证据的数字，而是可点击/可复核评分卡。B 延后到至少 30 张公开卡且数据更新成本被证明后；C 仅用于首批种子案例。

## 执行计划

以下是 60 天计划；GitHub 源码发布已经执行，其余动作仍按各自权限门推进。

| 时间 | Owner | 资产/动作 | 渠道与数量 | 预算 | 指标 | 通过阈值 |
|---|---|---|---|---:|---|---:|
| 0–14 天 | 维护者 | 发布 GitHub repo、npm 0.2.0、双语 README、10 张种子评分卡 | GitHub + npm，各 1 个正式入口 | 0 | 安装与生成成功 | 5 名新环境用户中 ≥4 成功 |
| 0–14 天 | 运营 | 提交结构化收录申请 | DSH Plugin Leaderboard、dsh.pub、dsharness.io 共 3 个正常提交入口 | 0 | 被收录数 | ≥2/3 |
| 0–14 天 | 维护者 | 发布 3 篇证据拆解：Stars≠质量、UNPROVEN≠FAIL、commit 绑定 | GitHub Discussion/README、Reddit/中文社区各 1 篇，不交叉刷屏 | 500 | 访问→CLI | ≥12% |
| 15–30 天 | 运营 | 邀请 15 位插件维护者自助生成卡片 | 每人 1 条定制、非群发消息 | 1,000 | 回复/完成 | ≥5 回复、≥3 完成 |
| 15–30 天 | 维护者 | 产出 GitHub Action recipe 和 5 个修复前后案例 | 文档 1 份、案例 5 份 | 0 | 重复运行 | ≥5 仓库采用 |
| 31–60 天 | 维护者 + 运营 | 每周更新 5 张卡、每两周一份生态质量观察 | 20 张卡、2 份报告 | 2,000 | 公开评分卡 | 累计 ≥30 |
| 31–60 天 | 运营 | 小额测试精准开发者内容投放 | 2 个渠道、每个 1,500 RMB 上限 | 3,000 | 完成卡 CAC | ≤100 RMB |
| 31–60 天 | 维护者 | 维护争议与更正日志 | 100% 公开更正，保留旧 commit 卡 | 0 | 事实争议率 | <10% |

推荐传播文案只有一句：**“别问这个 DSH 插件有多少 Stars；先看这个 commit 到底证明了什么。”**

## 不要做

1. 不按 Stars 重排“质量榜”，这会优化 G1 噪声并摧毁差异化。
2. 不群发私信、不蹭官方名义、不把 `dsh-plugin` topic 写成官方认可；只走正常目录提交和定制维护者邀请。
3. 不在尚未达到 30 张公开卡前开发重型托管平台；先证明 CLI→卡片→公开嵌入的传播循环。

## 验证

- **证明有效**：60 天内 ≥30 个仓库公开评分卡、访问→CLI ≥15%、CLI→完成 ≥25%、E2+ 卡片占比 ≥50%、事实争议率 <10%。
- **转向条件**：访问→CLI <8% 时重写首屏和 60 秒 demo；CLI→完成 <15% 时优先减少依赖/交互步骤；公开率 <20% 时访谈“不愿展示”的信任障碍，而不是加曝光。
- **停止条件**：连续 30 天新增公开评分卡 <5，或付费渠道 CAC >100 RMB 且自然渠道无改善，则停止投放；保留 CLI 和按需审核，不继续建站。
- **规模化条件**：公开卡 ≥30、至少 10 个仓库重复更新、目录愿意摄入机器 JSON 后，才进入托管 API/自动更新 badge 的下一阶段。
